WHAT WAS WRONG

Desktop scored 100, mobile 94 (92 on a second run). Everything on the
mobile report was green except two numbers: Largest Contentful Paint
2.7–2.9 s against a First Contentful Paint of 1.5 s, and Speed Index
4.2 s. The LCP element is the bio paragraph in the hero, and PSI put
its whole time down as "element render delay" — 2.4 s — with nothing
to load. The bio is prerendered in index.html; it needs no script, no
font, no fetch. So where did 2.4 s go?

Not into painting it. The bio paints in the first frame, and it did
before this change too. What moved was everything around that frame.

app.js is deferred. Deferred scripts run as soon as the parser is done
and the stylesheet is in — and on a real connection that is routinely
BEFORE the browser has produced its first frame. Reproduced locally
with 80 ms of latency on every asset: in about half the loads, app.js
had run, hit the Worker for /live, /dates, /crate and /youtube, and
rewritten the section heads, all before the first paint. The paint
came ~50 ms after the scripts.

PageSpeed's mobile score is not a measurement of that load. It is a
model: Lighthouse takes the unthrottled run and re-simulates it on a
slow 4G connection (150 ms round trips, 1.6 Mbps) with a 4× slower
CPU. For the largest paint, the model takes every request that had
STARTED before that paint and every script that had run before it, and
treats all of it as if the paint had waited for it. Four Worker
fetches to a fresh origin (three round trips of handshake before the
first byte), the Cloudflare beacon to another fresh origin, app.js's
execution at 4× — simulated on slow 4G, that is the 2.4 s. On desktop
the simulation uses 40 ms round trips and no CPU slowdown, so the same
graph adds a few hundred milliseconds and the score stays at 100.

That is also why the earlier reveal guard ("never hide what the reader
can already see") didn't close the gap: it stopped app.js from
repainting the bio, but the bio's timing was never the problem — the
requests in front of it were.

1. BOOT AFTER THE FIRST FRAME  (app.js)

Everything app.js does now runs from main(), and main() is scheduled
from afterFirstPaint():

  requestAnimationFrame → requestAnimationFrame → setTimeout(0)

The first rAF fires just before a frame is produced; a second one from
inside it cannot be scheduled until that frame has been presented; a
timeout from there runs after the second frame goes out. So main()
starts roughly two frames (~30 ms) after the first paint, and every
fetch, every layout read and every DOM write lands after the largest
paint, where the model no longer counts it. One rAF was not enough:
its timeout ran a few ms before the compositor stamped the paint, and
the /live fetch landed just inside the window.

A hidden tab never gets a frame, so there the boot goes straight to a
timeout, and a 1.5 s fallback covers anything else that could keep rAF
from firing. Whichever fires first wins; the others are no-ops.

Nothing visible moves. The hero was already on screen; the rail, the
section numbers and the clock arrive two frames later than they used
to, which is under the threshold of a blink.

Local Lighthouse, mobile preset, 80 ms latency on every asset, three
runs each:

                    FCP      LCP      SI
  before           2.0 s    2.5 s    2.7 s     (when the race lost)
                   1.7 s    2.0 s    1.7 s     (when it won)
  after            1.6 s    1.9 s    1.6 s     (every run)

The remaining FCP→LCP gap is the two preloaded scripts and the font,
which start with the stylesheet and are therefore in the model no
matter what. It costs nothing on the score.

2. FORCED REFLOW  (app.js, watch())

PSI flagged 94 ms of forced synchronous layout at app.js:1189 — the
getBoundingClientRect() in watch(). The loop set an attribute, then
measured, then added a class, then measured the next node; every
measurement after the first forced a full layout, and the loop ran
again after each section rendered. watch() now filters, measures every
node, then writes: one layout per sweep, however many rows.

3. THE CLOUDFLARE BEACON  (index.html, app.js, content.js)

Cloudflare Web Analytics was a <script type="module"> at the end of
the body. A module script is deferred by default, so it did not block
anything — but it starts downloading with the document, from a third
origin, which is a full handshake in the model, and Lighthouse listed
it in the critical request chain. app.js now appends the same script
(defer, same data-cf-beacon attribute) at the end of main(), two
frames after the first paint. The token moved to content.js as
config.cfBeacon, next to the other public IDs; "" loads nothing. Both
hosts stay in the CSP exactly as before.

NOT CHANGED, AND WHY

Minify CSS/JS (PSI: ~16 KiB). Would need a build step, and the point of
this repo is that there isn't one. GitHub Pages gzips everything and
the comments compress to almost nothing; the modelled cost is under
100 ms. Left as is.

Improve image delivery (PSI: 308 KiB, Discogs sleeves). Discogs serves
exactly two sizes on signed URLs — 150 and 600 — and a card is 260 CSS
px at 1.75× device pixels, i.e. 455 px. 150 is blurry at that density
and 600 is the only other option; there is nothing in between to ask
for. The sleeves are loaded as 150 first and upgraded on demand, which
is as far as it goes without an image proxy.

Cache lifetimes (PSI: 127 KiB). YouTube's thumbnails, 2 h TTL. Not
ours.

"Unused preconnect" on workers.dev and i.discogs.com. Diagnostic only,
no score weight, and both origins are used within the first second.
Left in place.
